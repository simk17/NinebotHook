# 九号出行 LSPosed 插件 — 技术说明与实现文档

基于当前代码（插件 v49）整理，说明各功能如何实现、配置方式，以及 MCP/JADX 分析得到的工作原理。

---

## 1. 项目概述

| 项目 | 说明 |
|------|------|
| **目标应用** | 九号出行 `cn.ninebot.ninebot` |
| **插件包名** | `com.ninebot.hook` |
| **配置文件名** | `theme_config`（与 AndroidManifest 中 `xposedsharedprefs` 一致） |
| **Xposed API** | 82，LSPosed 适用 |
| **日志版本** | `HOOK_LOG_VERSION = 49`（日志中显示「插件v49」） |

**配置读写**：  
- **写**：在模块进程内由 MainActivity / HookConfig 写入（`MODE_WORLD_READABLE`）。  
- **读**：在九号进程内由 NinebotHook 通过 `XSharedPreferences(MODULE_PACKAGE, "theme_config")` 读取，每次使用前 `sPrefs.reload()`。

---

## 2. 安装与激活

1. **激活模块**：在 LSPosed 中打开本模块。
2. **作用域**（必做）：
   - 勾选 **「九号出行」**；
   - 勾选 **本模块自身**，以便九号进程通过 XSharedPreferences 读到 `theme_config`。
3. **重启九号出行** 使 Hook 与配置生效。

---

## 3. 配置项与功能开关

| 配置 Key | 说明 | 默认 |
|----------|------|------|
| `enable_theme_show` | 1. 强制开启内测主题（themeShow=1、主题 Tab、入口） | true |
| `enable_theme_crack_paid` | 2. 破解主题费用（已拥有/我的主题库/72057/device/resource 等） | true |
| `enable_other` | 3. 其他：抓包、水印、反调试 | true |
| `enable_force_motor_display` | 4. 修改车辆型号（仪表盘时速、轨迹详情电摩展示） | false |
| `force_motor_vehicle_type` | 4 使用的车型 ID，默认 116 = 九号电动Dz110P | 116 |
| `enable_screen_cast_overlay` | 5. 投屏导航叠加（地图导航时在画面上叠加内容） | false |
| `server_url` | Web 日志服务器，如 `192.168.1.100:8765` | 空则用 ReportHelper 默认 |

兼容：若未设置 `enable_theme_show` / `enable_theme_crack_paid`，会回退到 `enable_theme_hack`。

## 4. 各功能实现说明

### 4.1 功能 1：强制开启内测主题

**效果**：云控未开放主题时，仍显示主题 Tab、主题入口，并进入带「车控/主题」的详情页。

**实现**：

| 层级 | 目标类 / 方法 | 动作 |
|------|----------------|------|
| 解密层 | `NeteaseDecrypt.decodeContent` | 解密后若含 `themeShow`，正则替换为 `"themeShow":1` |
| 内存层 | `TopGuideConfigRepository.getTopGuideTabConfig` | 对返回的 config 设置 `themeShow = 1` |
| UI 层 | `TopGuideDeviceDetailViewModel.updateTabList` | 在 Tab 列表中强制加入 `TopGuideTab.Theme` |
| 入口层 | `TopGuideDeviceDetailFragmentKt.isUseTopGuideMode` | 恒返回 `true`，强制走 TopGuide 详情页 |

**条件**：仅当 `isThemeShowEnabled()` 为 true 时执行上述篡改。

---

### 4.2 功能 2：破解主题费用

**效果**：主题显示为「已拥有」、我的主题库有内容、APP 皮肤可应用（含 72057 order not found 篡改、device/resource 注入 bgAnimation 与 APP 皮肤项）。

**实现**：全部在 **解密层** `NeteaseDecrypt.decodeContent` 的 `afterHookedMethod` 中，对解密字符串做正则/片段替换（仅当 `isThemeCrackPaidEnabled()` 且内容像主题相关时）：

- **已拥有/付费**：`owned`、`isPurchased`、`is_purchased`、`paid`、`hasPurchased`、`purchased`、`purchaseStatus` 等 → 改为 1/true。
- **推荐页 themeList**：缓存 `themeList` 数组 JSON，用于注入「我的主题库」空列表（`"themeList":[]` → 缓存的列表）。
- **主题详情/下载**：缓存 APP 皮肤项（resourceType:3）和 `downLoadUrl`，供 device/resource 注入用。
- **72057**：`"code":72057`、`"desc":"order not found"` → 改为成功，绕过订单校验。
- **device/resource**：  
  - 注入 `data.bgAnimation`（url 用缓存的 `cachedBgAnimationUrl`）；  
  - 在 `resourceList` 中注入 `cachedAppSkinResourceItem`（APP 皮肤项）。

**条件**：`isThemeCrackPaidEnabled()` 为 true，且解密内容包含 theme/skin 等关键字（`looksTheme`）。

---

### 4.3 功能 3：其他（抓包、水印、反调试）

**抓包**：  
- Hook `RetrofitStrategy.customizeOkHttpClient2`，在 Builder 上 `addInterceptor` 一个代理实现的 `Interceptor`。  
- 在 `intercept` 里对响应取 `body().string()`，用 `ReportHelper.report("抓包", "【URL】"+url+" 抓取到加密包")` 上报；异常时只打日志不抛，避免影响业务。  
- **条件**：`isOtherEnabled()`。

**车辆信息明文**：  
- 在 `NeteaseDecrypt.decodeContent` 中，若 `isOtherEnabled()` 且解密结果包含 `vehicle_type`，则调用 `reportVehicleInfoFromDecrypted(decrypted)`，用正则提取 `vehicle_type`、`wnumber`、`device_name`、`vehicle_name_zh`、`and_mac` 等，以 tag「车辆信息」上报，便于确认车型 ID。

**反调试**：  
- Hook `Debug.isDebuggerConnected()`，`afterHookedMethod` 恒 `setResult(false)`。  
- **条件**：`isOtherEnabled()`。

**水印**：  
- Hook `Activity.onResume`，若为九号包名且 `isOtherEnabled()`，则在 decorView 上添加半透明「Hook成功 当前插件版本 xxx」TextView（tag `ninebot_hook_watermark` 防重复）。

**Toast**：  
- Hook `Application.attach`，若为九号包名则 2 秒后 Toast「九号出行LSPosed插件 注入成功 v49」。

---

### 4.4 功能 4：修改车辆型号（仪表盘时速 + 轨迹详情电摩展示）

**需求简述**：  
- **数据与身份**：定位、轨迹列表、骑行日期/里程/次数、车辆上送等，一律保持**真实车型 116**（我的车）。  
- **展示**：仪表盘按电摩显示（如 km/h）、轨迹详情/分享页按电摩展示（时速、骑行时间），首页定位与最近骑行卡片显示 116 的数据。

**设计原则**：  
- 不全局改 `getVehicleType()` 为电摩 type（否则上送与列表身份会错）。  
- **身份**：`DeviceBean.getVehicleType()` 恒返回 **116**。  
- **展示**：仅在「仪表盘 UI」「首页卡片」「轨迹详情/分享」等展示链路上，通过**单独 Hook** 注入电摩配置或改写展示用参数。

#### 4.4.1 getVehicleType 统一为 116

- **Hook**：`DeviceBean.getVehicleType()`，`afterHookedMethod`。  
- **逻辑**：若 `isForceMotorDisplayEnabled()`，则无论原返回值多少，一律 `param.setResult(116)`。  
- **作用**：所有依赖 `getVehicleType()` 的**身份/数据**（列表、定位、上送、统计）都视为 116。

#### 4.4.2 仪表盘与首页卡片的四层 Hook

仪表盘和首页卡片依赖：`DeviceBeanExtKt.getConfig(DeviceBean)`、`createDynamicDeviceDetailPage(DeviceBean)`、`DynamicPageViewModel` 的 `deviceConfig`、以及首页卡片的 `serverId`。下面四层仅当 `isForceMotorDisplayEnabled()` 时生效。

| 层 | 目标 | 动作 |
|----|------|------|
| A | `DeviceBeanExtKt.getConfig(DeviceBean)` | `beforeHookedMethod`：用 `DynamicConfigManager.getDeviceConfigWithServerId(forceType)` 得到电摩 config，`setResult(config)`，覆盖 isMotor/isEleBike 及通过 getConfig 取 page 的路径。 |
| B | `DynamicDeviceDetailFragmentKt.createDynamicDeviceDetailPage(DeviceBean)` | `beforeHookedMethod`：用 forceType 的 config 取 `modelName`，经 `DynamicDeviceModels.Companion.findByName(modelName)` 得到 model，再 `model.createDetailUi(bean)` 得到 Fragment，`setResult(fragment)`，直接创建电摩详情 Fragment。 |
| B2 | `DynamicPageViewModel` 构造函数 | `afterHookedMethod`：仅当 `configName` 为**白名单**（`device_ui_dashboard`、`device_ui_detail` 或 null/空）时才用 forceType config 替换 `deviceConfig`；其余 configName（更多设置、仪表设置、骑行模式设置等子页）**不替换**，保持 116，避免子菜单显示电摩界面或内容为空。 |
| C | `NavigationViewController` / `RecentTrailViewHolder` 构造函数 | `beforeHookedMethod`：若第 3 个参数为 Integer，则改为 `116`，保证首页「定位」「最近骑行」卡片请求与展示的是 116 的数据。 |

**MCP 结论**：  
- `DynamicDeviceModels` 为 Kotlin object，静态实例为 **Companion**（不是 INSTANCE）。  
- 仪表盘页面配置来自 `DynamicPageViewModel.deviceConfig`，在构造函数中赋值；LoadConfigFragment 为 final，且 MotorDeviceDetailV2Fragment 不继承它，因此改 `deviceConfig` 在 ViewModel 构造时最直接。

#### 4.4.3 轨迹详情/分享仅改展示

- **不改身份**：轨迹列表、接口、定位仍用 116；仅进入「轨迹详情页」或「分享页」时，把**传给 RN/详情页的数据**里的展示用字段改为电摩。
- **改写内容**：对 JSON 或对象中的 `vehicleType`/`vehicle_type` 改为 `forceType`，`hide_speed` 改为 false；必要时补 `vehicleType`+`hide_speed` 字段。
- **Hook 点**：  
  1. `TrackResult.copy()`：对 copy 出的对象 `setVehicleType(forceType)`。  
  2. `RNProviderImpl.toRNPage(String module, Map params)`：若 module 为 `"Track"`，遍历 params 中值为 String 且形如 JSON 的项，用 `rewriteTrackDetailType(s, forceType)` 改写后写回。  
  3. `RNProviderImpl.toOtherTrackDetail(String)`：对第一个参数做 `rewriteTrackDetailType` 后写回。  
  4. `DevicePage.PLAY_TRACK.navigate(..., String parameters)`：对第二个参数做 `rewriteTrackDetailType` 后写回。

### 4.5 功能 5：投屏导航叠加

**效果**：当用户选择「地图导航」并开始投屏时，在**被采集的 View** 上包一层容器，并叠加一层自定义 View（当前为 1mm 网格线，用于验证是否绘制到车机）。

**实现**：  
- **入口**：不直接依赖首屏类；通过 `ClassLoader.loadClass` 监听，当加载到 `DeviceApplication` 时，Hook `DeviceApplication.init(Context)`，在 `afterHookedMethod` 里用 `context.getClass().getClassLoader()` 再调用 `tryHookScreenCastOverlay(loader)`，从而在 CaptureClient 已存在的 ClassLoader 上挂载投屏 Hook。  
- **MCP 结论**：`CaptureClient`、`CaptureService` 在 **classes17.dex**，首屏不会加载；`DeviceApplication.init()` 内会调用 `CaptureClient.INSTANCE.setNotificationCreator(...)`，init 执行时 CaptureClient 已加载。  
- **Hook 点**：  
  1. `CaptureClient.createCapture(..., View captureView, int width, int height, ...)`：将 `param.args[2]` 替换为 `wrapCaptureViewWithOverlay(original, w, h)`（原 View 作为子 View，上层叠加 `Grid1mmOverlayView`）。  
  2. `CaptureClient$CaptureControllerWrapper.replaceView(View)`：同样用 `wrapCaptureViewWithOverlay` 替换传入的 View。  
  3. `CaptureService.createCodecCapture` / `createMpeg2Capture(View, int, int, ...)`：第一个参数 View 同样用 `wrapCaptureViewWithOverlay` 替换。  

**条件**：`isScreenCastOverlayEnabled()`。  
**注意**：若完全替换为仅文案 View，车端可能回退到简易投屏；当前采用「原 View + 叠加层」以保留地图并验证叠加是否上屏。

## 5. Hook 安装与类加载

- **installHooks(loader)**：  
  - 先执行一次 **tryHookAll(loader)**；  
  - 再 Hook `ClassLoader.loadClass`，在 `afterHookedMethod` 中：  
    - 若加载的类名为 `cn.ninebot.device.DeviceApplication`，则调用 `hookDeviceApplicationInitThenScreenCast(clazz, targetLoader)`；  
    - 若类名包含 ninebot 且包含 capture/Capture/screencast/ScreenCast，则对该 ClassLoader 执行 `tryHookAll`；  
    - 若仅包含 ninebot，则对传入的 loader 执行 `tryHookAll`。  
- **tryHookAll** 依次调用：  
  tryHookRetrofit → tryHookDecrypt → tryHookMemoryConfig → tryHookThemeUI → tryHookEntry → tryHookDashboardAndHomeCards → tryHookDeviceBeanVehicleType → tryHookTrackDetailDataObjects → tryHookScreenCastOverlay。  
- 各 tryHook* 内部用 `findClassIfExists` + 布尔标志位（如 `hookedRetrofit`）避免重复挂载。

## 6. MCP/JADX 分析结论与工作原理

以下为基于反编译代码（JADX）分析得到的结论，用于解释实现方式和排错。

### 6.1 电自/电摩显示逻辑

- **统一数据源**：`DeviceBean.vehicleType`（int），来自服务端 API、本地 DB、BLE 的 DeviceModel.getId()。  
- **仪表盘**：是否显示 W/% 还是时速，由当前设备的 vehicleType 对应的 **DynamicDeviceConfig** 决定；详情页通过 `DeviceBeanExtKt.getConfig(deviceBean)` → `DynamicConfigManager.getDeviceConfigWithServerId(vehicleType)` 取配置，再决定用哪个 Fragment/模板（如 Motor 系）。  
- **轨迹**：列表与详情是否「仅时间+耗电」还是「详情（时速等）」由传入的 vehicleType 或 JSON 中的 vehicleType/hide_speed 等控制；入口多为 `RNProviderImpl.toRNPage("Track", ...)`、`toOtherTrackDetail`、`DevicePage.PLAY_TRACK.navigate`。  
- **未配置的 vehicleType**：若 117、118 等没有对应动态配置，会落到「未知车型」分支，出现「发起导航(体验版)」「仅支持高德自行车」等，并非两个独立内部功能，而是同一套 fallback。

### 6.2 投屏导航（BLE + WiFi）

- **蓝牙（BLE）**：连接车辆、拉取投屏配置（ScreenCastConfig）、下发导航指令（DashNaviDataMessenger：setNaviStart、setNaviInfo、距离、路名等）；若通道为 BLE，画面也走 BLE（RTP）。  
- **WiFi（Wifi P2P）**：与车机建链；当配置为 WIFI/WIFI_KCP 时，画面/视频流走 WiFi。  
- **配置**：channel/rtpChannel 等由**车端**通过 BLE 下发，APP 用 `ScreenCastConfigClient` 读车端文件得到。  
- **画面来源**：不是「先录屏再叠数据」；而是按 **ScreenCastConfig.layout** 用 **NaviScreenCastLayoutInflater** 拼出一棵**投屏用 View 树**（地图 + 距离/转向等），再对该树的**根 View** 做采集、编码、RTP 发送。  
- **采集入口**：`CaptureClient.createCapture` / `createCodecCapture` / `createMpeg2Capture` 传入的 **captureView** 即该根 View；Hook 此处可替换或包装「被编码的内容」。

### 6.3 投屏 Hook 可行性

- **替换/包装被采集的 View**：在 `createCapture`、`replaceView`、或 `CaptureService.createCodecCapture/createMpeg2Capture` 处，把传入的 View 换成自定义 View 或包一层叠加 View，即可改变投到车机的内容。  
- **注意**：CaptureService 的 createCodecCapture/createMpeg2Capture 为 **native 实现**，若仍不生效需考虑 native 是否使用 MediaProjection 等其他源。  
- **验证**：adb logcat 过滤 `NinebotHook/投屏`、`NinebotHook`；若出现「DeviceApplication.init 已执行」「createCapture 已挂载」「createCapture 已调用」说明 Hook 已安装并执行。

## 7. 代码与配置结构

- **NinebotHook.java**：唯一 Hook 入口，实现 `IXposedHookLoadPackage.handleLoadPackage`，所有 tryHook* 与工具方法。  
- **HookConfig.java**：配置 Key 常量与 get/set（ThemeShow、ThemeCrackPaid、Other、ForceMotorDisplay、ForceMotorVehicleType、ScreenCastOverlay、ServerUrl），使用 `theme_config`。  
- **MainActivity**：开关与输入框绑定 HookConfig，保存设置；快捷操作：停止九号、重启九号、启动九号（需 root 的 am force-stop）。  
- **ReportHelper**：logcat 打日志并异步/同步推送到 Web（tag + msg），服务器地址来自 HookConfig 或 setCustomServerUrl（九号进程内由 Hook 从 sPrefs 读 server_url 注入）。  
- **ConfigProvider**：LSPosed 模块配置（若使用）。

## 8. 常见问题与处理

| 现象 | 处理 |
|------|------|
| 主题/车型不生效 | 确认 LSPosed 作用域已勾选九号+本模块，并重启九号；配置修改后也需重启九号。 |
| 车辆信息看不到 vehicle_type | 开启「其他」、配置 Web 服务器并保存，打开九号进设备/详情触发接口，在 Web 日志 tag「车辆信息」中查看。 |
| 填了 117/118 出现「发起导航(体验版)」「仅支持高德自行车」 | 这些 ID 无对应动态配置，会走未知车型分支；用抓包得到的真实电摩 type（如 14101）或保持 116。 |
| 仪表盘仍是 W/% | 确认已开「修改车辆型号」且 force_motor_vehicle_type 为有配置的车型（如 116 或已抓包的电摩 type）；查看日志是否有「DPVM_CONFIG_FORCE」「DASHBOARD_FRAGMENT_FORCE」。 |
| 定位/轨迹列表变成别车 | 插件设计为 getVehicleType() 恒 116，身份应一致；若异常可查是否其他模块或版本差异，并看「车型判定」日志。 |
| 投屏无叠加/无日志 | 确认「投屏导航叠加」已开；开始**地图导航**（非简易导航）后看 logcat「NinebotHook/投屏」是否有「createCapture 已调用」；若无，确认 DeviceApplication.init 与 CaptureClient 已加载（见 6.3）。 |
| 抓包/上报失败 | 检查 server_url、网络可达性；读取 body 失败时拦截器会打日志但不抛异常，不影响业务。 |

## 9. 调试与日志

- **logcat**：所有上报都会 `Log.i(TAG, "[" + tag + "] " + msg)`，TAG 为 `NinebotHook`；车型相关为 `NinebotHook/车型`，投屏为 `NinebotHook/投屏`。  
- **Web 上报**：`ReportHelper.report(tag, msg)` / `reportSync`，GET 到 `server_url/report?tag=xxx&msg=xxx`。  
- **车型判定**：前几次 `getVehicleType` 强制 116 时会打「FORCE_116 real=xxx ret=116」及「车型判定」上报，便于确认身份是否统一。  
- **车辆信息**：开启「其他」且解密内容含 vehicle_type 时，会以「车辆信息」上报明文 vehicle_type、wnumber、device_name 等，便于确认默认车型 ID。
